## Storage architecture

### Candidates and selection

One JSON file per Lead is selected: it gives a small corruption radius, same-directory atomic publication, deterministic recovery, independent migration, and test isolation. A consolidated JSON/YAML collection is rejected because every capture rewrites and locks all records. SQLite is deferred because it adds extension/operational dependency and a single-artifact blast radius. Flex Objects are deferred pending a later exact query/migration audit. Future Phase 4 scans records until an independently rebuildable index is justified.

Canonical root and layout:

```text
user-data://goosialize-leads/
  v1/
    .capture.lock
    records/YYYY/MM/<32-lowercase-hex-id>.json
    idempotency/<first-two-digest-characters>/<64-lowercase-hex-key-digest>.json
```

There is no mutable search index initially; idempotency sidecars are transactional mappings. Directories request `0700`; records, sidecars, lock and temporary files request `0600`, with effective modes verified or capture fails closed. Records are canonical UTF-8 JSON using exception-on-error, unescaped Unicode/slashes, stable key order, and one LF. Maximum serialized size is 32 KiB. Initial capacity assumption is 10,000 records/month directory; beyond that requires sharding/index review.

The full root, including sidecars, is the backup boundary. It lies outside the plugin package, survives upgrades, and is retained on uninstall by default. Retention duration and authorized erasure require later policy.

Reject a symlink at the root or any component. Walk existing components with `lstat`, require directories/regular files as appropriate, canonicalize parents, and enforce separator-aware containment. Externally supplied values never construct filenames.

### Atomicity and concurrency

The sole publication primitive is same-filesystem hard-link creation after a complete temporary write. Exact PHP 8.5.8 probing proved that `link($temporaryPath, $finalPath)` exposes the complete pre-written inode, preserves `0600`, and returns failure when the final path exists. Plain `rename()` is not the no-replace boundary, there is no overwrite fallback, and unsupported hard-link publication fails closed.

1. Resolve the absolute root; safely create and revalidate each directory, symlink status, containment, and effective `0700` mode.
2. Validate/open `v1/.capture.lock` at `0600`; acquire blocking `flock(LOCK_EX)`. It is the only Phase 3 lock.
3. Validate idempotency under the lock using the canonical sidecar contract.
4. Generate 16 random bytes and retry at most five ID collisions.
5. Exclusively create a random same-directory record `.tmp-<32-lowercase-hex-id>-<16-lowercase-hex>.json` or sidecar `.tmp-sidecar-<64-lowercase-hex-key-digest>-<16-lowercase-hex>.json` with `fopen(..., 'x+b')`, mode `0600`.
6. Serialize before writing; loop through all bytes, verify length, call/check `fflush` and available `fsync`, recheck regular-file/symlink/containment/mode state, then close the handle.
7. Publish only with `link($temporaryPath, $finalPath)`. Existing destination means collision: records regenerate within the bounded limit; sidecars validate the existing mapping. Never replace it.
8. Verify final regular file, inode, size, mode and containment, then unlink only the validated temporary name. Readers consume only canonical final filenames; temporary names are never records.
9. Publish the canonical sidecar by the same algorithm. If interrupted after record publication, return 503 and use the documented bounded recovery scan on retry.
10. Release in `finally`; remove only validated contained temporary files from the current attempt.

Unique submissions serialize and succeed. Same-key submissions create at most one record/sidecar; exact replay does no write or notification. Termination before link leaves a temp; after link but before temp unlink leaves a valid final plus temp; after record link but before sidecar link invokes recovery. Full disk, short write, permission/mode failure, malformed state, invalid filename, unsupported links, or collision exhaustion fails closed without replacing data. Process exit releases `flock`; no stale-lock deletion exists.

Current-request cleanup is step 10 and removes only a validated temporary created by the same call. Phase 3B never scans publication directories and never deletes a temporary left by another process. Stale/post-crash cleanup, authorization, active-write detection, bounded scans, maintenance results/events, and a CLI entry point are deferred together to Phase 7. Anonymous capture, Forms, API, Admin2, plugin startup, and Phase 3B invoke no cleanup operation beyond same-call `finally` cleanup.

Hard-link atomicity is limited to the verified local same-filesystem contract. Phase 3B guarantees process-visible atomic no-replace publication, not persistence of directory entries across power loss. Directory `fsync`, network/overlay filesystem crash semantics, scheduled cleanup, and post-crash temporary cleanup are explicit Phase 3B non-goals. Absence of directory `fsync` is not a runtime failure. File contents must still be completely written, flushed, and successfully `fsync()`ed before publication. Tests prove that readers see either no final entry or one complete final entry and document that power-loss durability remains an operator/filesystem responsibility.

## Validation pipeline and idempotency

Order is: method/length transport checks; media type; byte-counted read; UTF-8 JSON parse at depth four; duplicate-member detection; root/field/depth shape; allowlist; types; NFC/whitespace/line normalization; semantic lengths and formats; consent; idempotency; record construction; atomic storage; response; PII-free log.

Maximum request fields are 11 allowlisted top-level members plus the consent child and five campaign children. PHP JSON overwrites duplicate keys, so Phase 3C must prove the raw duplicate detector defined in the verification table before decoding. Phase 3A owns and verifies `ext-intl`/NFC availability; later checkpoints rerun it only as regression coverage and always fail closed rather than silently skip. Controls/noncharacters are rejected except message LF. HTML is unsupported: tag-like markup is rejected, and later output must still escape. Only message is multiline, at 4,000 code points/8,000 bytes.

The opaque client key is not identity. Store only `SHA-256(key)` and an `HMAC-SHA-256` fingerprint of canonical normalized submitted fields. Do not store separate email/phone hashes. Canonical sidecars expire after 30 days but are removed only by authorized maintenance; capture never overwrites or deletes them. Exact reuse returns 200; changed payload returns 409; no key always creates a new legitimate Lead. Concurrent matches serialize. Replays consume rate limit and authorize no reads. The server HMAC secret uses the versioned Phase 3B contract and must pass the generation, rotation, backup and uninstall probe in the verification table.

## Notification contract

Phase 3 attempts one notification only after a newly created Lead and sidecar are durable. ### Storage locator, containment, names, modes, and publication

`FilesystemLeadRepository::__construct()` accepts exactly one trusted absolute canonical `user-data://` filesystem root, already resolved by Grav composition, and appends only `goosialize-leads/v1`. It rejects empty, relative, NUL-containing, stream-wrapper, dot-segment, trailing-dot-segment, and noncanonical paths. It never accepts the plugin-relative root or a visitor-derived path. On Windows drive syntax is unsupported; Phase 3B supports the pinned Linux deployment only.

The constructor lexical-normalizes repeated separators and a single trailing separator, requires the supplied existing user-data root to have `realpath()`, requires it to be a non-symlink directory by `lstat()`, and stores its canonical path. Each existing descendant is checked with `lstat()` before `realpath()`, must not be a symlink, and must remain separator-aware within the stored root. Missing descendants are created one component at a time with `mkdir(..., 0700)`, immediately `chmod(..., 0700)`, then rechecked with `lstat()`, `realpath()`, containment, ownership type, and exact `0700 & 0777`. A missing component whose parent cannot be canonicalized fails `root_invalid`. Any root/component symlink fails `symlink_detected`. No arbitrary absolute child or `..` is accepted.

All directories are exactly `0700`; lock, temporary, record, and sidecar files are exactly `0600`. The repository temporarily sets `umask(0077)` only around creation, restores it in `finally`, calls `chmod()` explicitly, and verifies `fileperms() & 0777`. It assumes the PHP process owns newly created paths; ownership mismatch or inability to verify exact modes fails `permission_failed`. Errors expose no path.

The lock path is exactly `goosialize-leads/v1/.capture.lock`. It is opened with `fopen($path, 'c+b')`, immediately validated as a contained non-symlink regular file, explicitly chmodded and verified as `0600`, and acquired with blocking `flock($handle, LOCK_EX)`. One repository call owns it until all replay, collision, record, sidecar, recovery, and current-temp cleanup decisions finish. `flock($handle, LOCK_UN)` and `fclose()` run in nested `finally` blocks; acquisition, unlock, or lock-handle close failure maps to `lock_failed`. No lock file is deleted or treated as stale.

Final record path is `records/YYYY/MM/<32-lowercase-hex-id>.json`. Final sidecar path is `idempotency/<first-two-key-digest-characters>/<64-lowercase-hex-key-digest>.json`. UTC year/month come only from the canonical record timestamp. Maximum final basenames are 37 and 69 bytes respectively.

Temporary record basename is `.tmp-<32-lowercase-hex-id>-<16-lowercase-hex>.json` (59 bytes). Temporary sidecar basename is `.tmp-sidecar-<64-lowercase-hex-key-digest>-<16-lowercase-hex>.json` (99 bytes). The repository invokes `$temporaryEntropy(8)` exactly once per temporary creation; it must return exactly eight bytes, encoded with lowercase `bin2hex()`. Throwable or wrong-length output maps to `temporary_creation_failed`. Files are opened only with `fopen($path, 'x+b')`.

The complete byte string is prepared before opening. Writes loop until all bytes are accepted; `false` maps to `write_failed`, zero or incomplete termination maps to `short_write`. Then `fflush()` and `fsync()` must return true, mode/type/containment are revalidated, and `fclose()` must return true. Failure maps respectively to `flush_failed`, `file_fsync_failed`, or `close_failed`. The handle is closed in `finally`; only the validated current-attempt temporary is unlinked.

Publication uses only same-directory `link($temporaryPath, $finalPath)`. No `rename()`, copy, overwrite, or fallback exists. Once per repository instance, inside the acquired lock and before inspecting or publishing a request, the repository creates `v1/.probe-link-<16-lowercase-hex>` with `fopen(..., 'x+b')`, writes the exact bytes `phase-3b-link-probe\n`, flushes/fsyncs/closes it, hard-links it to `v1/.probe-link-<same-hex>.linked`, verifies equal nonzero inode and exact bytes, then unlinks the linked name followed by the source name. The same constructor temporary-entropy callable supplies exactly eight bytes for the suffix. Any pre-existing probe name, failed operation, unequal inode/bytes, or cleanup failure maps to `publication_unsupported`; both names are current-operation artifacts removed in `finally`. Probe names are never records, sidecars, or reader candidates.

An already existing canonical record final returns `PersistenceResult::idCollision()` after validating that it is a non-symlink regular contained file; its bytes are never changed. An existing sidecar is strictly parsed and verified against its referenced canonical Lead and historical key version. The candidate request record’s `capturedAt()` is the injected current request time used for expiry comparison; `capturedAt() >= expires_at` returns `idempotency_expired`. Before expiry, matching historical-version HMAC returns `replayed`, a different payload returns `idempotency_conflict`, and malformed state throws `idempotency_index_invalid`. Other record `link()` failure maps to `publication_failed`; sidecar `link()` failure maps to `sidecar_publication_failed`.

For every keyed request, after checking for an existing sidecar and before publishing the candidate record, the repository performs the missing-sidecar recovery scan. It walks only validated non-symlink `records/YYYY/MM` directories in ascending lexical `YYYY/MM/filename` order and examines at most 10,000 canonical final record names across the entire contained `records` tree. It validates each examined record’s exact schema, filename/ID, size, mode, containment, key hash, key version, and payload fingerprint, and calls `IdempotencyKeyRing::verify()` with that record’s historical version and the request payload bytes. Zero matches permits new record publication; exactly one matching record causes publication of its missing sidecar and returns `replayed`; multiple matches, an anomaly, or encountering a 10,001st canonical record fails `idempotency_index_invalid`. Thus a retry in a later UTC month cannot miss an earlier orphan and cannot create a second keyed Lead.

For keyed creation, the record publishes first and the sidecar second. If sidecar publication fails, the published record remains immutable and the operation returns `sidecar_publication_failed`; it is never rolled back because unlinking a visible Lead would lose accepted data. A later same-key request executes the pre-publication recovery scan above. Unkeyed creation ends after record publication. Readers never consume temporary names.

### Route, lifecycle, and transport

The sole route-registration hook is `onApiRegisterRoutes`. `GoosializeLeadsPlugin::onApiRegisterRoutes()` obtains the event’s `ApiRouteCollector` and calls `post('/goosialize-leads/capture', [PublicLeadApiController::class, 'capture'])`. Separately, `onApiCollectPublicRoutes` does not register a route: it appends the exact method-scoped string `POST /api/v1/goosialize-leads/capture` to the event’s `exact` list so only this POST bypasses API authentication. The sole full path is `/api/v1/goosialize-leads/capture`; it has no route name, locale prefix, configurability, or trailing-slash alias. API-plugin absence means its events never fire and the plugin remains loadable with no route. Disabled or invalid public-API configuration likewise registers no route or public classification while Forms remains available. A conflicting route is a configuration failure: this plugin registers no alternative.

The plugin also subscribes to Grav `onRequestHandlerInit` at priority 98000. The API plugin registers its `ApiRouter` at priority 99000; this plugin then prepends `PublicApiRawBodyMiddleware`, so its raw stream check executes before API `JsonBodyParserMiddleware`. The middleware handles only the exact path. It requires a seekable stream, rewinds it, reads at most 16,385 raw bytes, and rewinds again; non-seekable, rewind, or read failure returns `request_unavailable`. It never trusts Grav/API parsed-body values.

Only POST is allowed. Other methods, including OPTIONS, return 405 and `Allow: POST`; no preflight or credentialed CORS facility exists. `Content-Type` must be `application/json` with either no parameter or exactly one case-insensitive `charset=utf-8`; every other type, charset, duplicate parameter, or malformed value is 415. `Accept` may be absent, `*/*`, `application/json`, or a comma-separated list containing either media range; otherwise 406. All responses are UTF-8 JSON with `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and `Vary: Origin`. No `Access-Control-Allow-Credentials` is emitted. An allowed cross-origin response echoes its canonical Origin in `Access-Control-Allow-Origin`; same-origin emits none.

### Raw JSON, Origin, and abuse controls

The raw-body limit is exactly 16,384 bytes inclusive. Empty means zero bytes. UTF-8 is checked with `preg_match('//u', $bytes) === 1`; a UTF-8 BOM is invalid JSON. Root depth is 1 and maximum nesting depth is exactly 4. Before `json_decode()`, a single-pass byte scanner tracks strings, escapes, arrays, objects, and object-member positions, decodes JSON string escapes including surrogate pairs solely for key comparison, and rejects a decoded duplicate name within the same object; nested objects have independent sets. It rejects malformed escapes and invalid surrogate pairs. Then `json_decode($bytes, true, 4, JSON_THROW_ON_ERROR | JSON_BIGINT_AS_STRING)` must consume the entire input and produce an object. Any JSON number anywhere is rejected as `request_schema_invalid`; no accepted field uses a number. Trailing non-whitespace bytes, excessive depth, arrays/scalars at root, and duplicates have their named failures. Strings retain JSON escape semantics and enter Phase 3A unchanged. Unknown members are rejected; no first-value selection or coercion exists.

`Origin` is mandatory and exactly one header value. `null`, comma-joined/multiple, malformed, credential-bearing, path/query/fragment-bearing, non-HTTP(S), Unicode/IDNA, or trailing-dot origins are rejected. Hosts are canonical ASCII lowercase; IPv4 and bracketed IPv6 must parse canonically. Default ports 80/443 are removed and every other explicit port is preserved. An Origin is allowed only if it exactly equals the canonical direct request URI scheme/host/port or an exact canonical entry in `plugins.goosialize-leads.public_api.allowed_origins`. Wildcards are forbidden. No source-proven proxy-address allowlist exists in Grav 2.0.12, so `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Port`, and `X-Forwarded-Proto` never influence origin or client identity, regardless of sender.

Rate limiting occurs after path, method, negotiation, raw-size, and Origin checks but before JSON parsing. The key is the canonical direct server `REMOTE_ADDR` only: canonical IPv4 or lowercase compressed IPv6; missing or invalid address fails closed. It is a fixed window of 10 accepted checks per 60 seconds with no extra burst. State survives process restart under `<user-data>/goosialize-leads/v1/api-rate-limit/`, directory mode 0700 and regular lock/state files 0600. The filename is lowercase SHA-256 of canonical address; file content is exact JSON `{"window_start":<integer>,"count":<integer>}` plus LF. One exclusive `flock()` covers read, validation, increment, truncate/write/flush, and unlock; symlinks, non-regular files, wrong containment, malformed state, permission failure, lock failure, or I/O failure return 503. The injected integer Unix-seconds clock defines windows. Each allowed check removes at most 100 expired regular state files while holding a separate cleanup lock; symlinks are ignored. At 10,000 state files, unknown keys fail closed until cleanup reduces the count. Limited requests return 429 with `Retry-After` equal to `window_start + 60 - now`, minimum 1.

## Phase 5A durable notification outbox

### Integration and failure policy

`LeadCaptureService::mapPersistenceResult()` is the sole integration point. After it validates the complete record from `PersistenceResult::created()` or `replayed()`, it constructs `NotificationEvent::fromLeadRecord($record)` and calls `NotificationOutbox::ensure()`. No earlier layer may enqueue. A created or replayed Lead returns the existing unchanged `CaptureResult::success()` regardless of enqueue result. `created`/`existing` are silent; failure invokes the injected stable-code logger once and is otherwise concealed. Validation/conflict/storage failures never enqueue. Forms and JSON therefore have identical semantics and unchanged responses.

Outbox failure never rolls back, deletes or rewrites a Lead or sidecar. An identical replay calls `ensure()` and repairs a missing event. A conflicting replay never reaches this point. Invalid/missing outbox configuration supplies no outbox and leaves capture successful; `notifications.outbox.enabled: false` is the default. There is no delivery, network call, recipient, template or notification response field.

### Storage and concurrency

Root is `<user-data>/goosialize-leads/v1/notification-outbox/events/`. The event path is `<first-two-event-ID-hex>/<64-hex-event-ID>.json`; root and shard directories are non-symlink mode 0700, files mode 0600. Maximum root/shard entries are respectively 256/10,000; exceeding either returns `outbox_capacity_exceeded`. Event bytes are canonical per the data contract and at most 512.

Each ensure operation uses contained non-symlink paths and a sibling `<event-id>.lock` mode 0600 with exclusive `flock`. It creates a same-directory `.event-<event-id>-<16-lower-hex>.tmp`, where the suffix is exactly eight entropy bytes encoded as lowercase hexadecimal, using exclusive creation/no-follow semantics. It writes all bytes, flushes and requires successful `fsync()` of the file, then publishes by hard-link no-replace, unlinks the temporary and requires successful `fsync()` of the opened shard directory. It never overwrites. Existing destination bytes are opened no-follow, bounded to 513 bytes and compared byte-for-byte with canonical bytes. Exact match returns `existing`; malformed, oversized or different bytes return `outbox_event_conflict`. Publication races reread/compare: a matching winner returns `existing`, otherwise conflict. One entropy draw and one publication attempt are permitted; temporary files are removed on every failure and the lock file may remain as an inert 0600 synchronization artifact. An unavailable/failed fsync returns `outbox_unavailable` without touching the Lead. Capacity counts all directory entries, including lock and temporary artifacts, before creating a new entry.

Simultaneous identical captures yield one Lead and one exact event. Simultaneous ensures have one `created` and matching losers `existing`. Event-ID collision, malformed/oversized existing event and conflicting bytes fail closed without overwrite. Directory, permission, lock, temporary-write, fsync, link, disk-full and cleanup faults map to `outbox_unavailable`; containment/symlink/type/mode faults map to `outbox_security_invalid`; capacity maps as above. Logs contain only these stable codes.

## Phase 5B bounded notification delivery

### Command and delivery guarantee

Grav auto-discovers `cli/DeliverNotificationsCommand.php` as `Grav\Plugin\Console\DeliverNotificationsCommand`, a final `Grav\Console\ConsoleCommand`. `configure(): void` sets only name `deliver-notifications`, description `Deliver pending Goosialize Lead notifications once`, and option `--limit` (`-l`, required value, default string `10`). Invocation is exactly `php bin/plugin goosialize-leads deliver-notifications --limit=10`. `serve(): int` calls `initializePlugins()`, validates canonical decimal `1` through `50`, composes dependencies from `user-data://` and plugin routing configuration, then calls the worker once. It has no argument, alias, dry-run, watch or scheduling mode.

Standard output contains at most one line per non-success category, `ERROR code=<stable-code> count=<n>`, in code lexical order, followed by exactly one final line `RESULT discovered=<n> delivered=<n> contended=<n> failed=<n> uncertain=<n>`. Standard error is always empty; the inherited Grav console style writes the bounded operational report to its supplied output stream, so Phase 5B does not invent a second output channel. No identifier, address, Lead/event content, path, exception or transport detail is printed. The worker continues through its discovered bound after an event failure. Reaching the requested bound is not an error; only those selected events contribute to this invocation's counters.

Delivery is explicitly at-least-once. No event is removed before transport success. A crash before the transport call leaves it pending. A crash during transport has unknown provider outcome and leaves it pending. A crash after provider acceptance but before durable archive can cause a later manual invocation to deliver again; exact-once delivery is not claimed. After a successful archive link but before pending unlink, the next run detects identical archived bytes and removes the pending duplicate without transport. ### Pending discovery, lock and archive

Pending root remains `<user-data>/goosialize-leads/v1/notification-outbox/events/`; event names remain `<first-two-event-ID-hex>/<64-lower-hex-event-ID>.json`, mode 0600 under mode-0700 directories, canonical and at most 512 bytes. ## Phase 5C.1 durable delivery state, retry and reconciliation

### State machine, clock and backoff

The delivery-state schema is exact in the data contract. State root is `<user-data>/goosialize-leads/v1/notification-outbox/delivery-state/<2hex>/<event-id>.json`; state-lock root is the sibling `delivery-state-locks/<2hex>/<event-id>.lock`. State locks are reusable mode-0600 files in mode-0700 contained directories using `flock(LOCK_EX|LOCK_NB)`. `FilesystemPendingNotificationRepository::withLockedEvent()` owns the existing delivery lock and creates one callback-scoped `DeliveryEventLease`; every stateful workflow acquires that delivery lock first and each state operation acquires the state lock second. The delivery lock remains held continuously through final state reread, secure event/Lead/message prerequisites, classification, archive or dead-letter work, state CAS, cleanup, and callback return. A `finally` releases it; contention returns `delivery_contended`; a lease used after callback return throws redacted `delivery_lease_invalid`. There is no unlock/relock handoff and state pathnames never convey ownership.

Production time is `SystemDeliveryClock::now()`, a fresh UTC `DateTimeImmutable`; tests inject a fake `DeliveryClock`. Canonical time is `Y-m-d\TH:i:s.u\Z`. A value earlier than current state `updated_at`, unavailable/invalid time, arithmetic overflow or year beyond 9999 returns `state_clock_invalid` before transport. Forward jumps are accepted. Eligibility is exact wall-clock comparison `now >= next_eligible_at`; monotonic duration is not claimed across processes.

Maximum attempts are 5. After an explicitly classified retryable negative at attempt 1, 2, 3 or 4, next eligibility is respectively attempt timestamp plus 300, 1,800, 7,200 or 28,800 seconds. Attempt 5 retryable negative is terminal and dead-letters. There is no jitter or configurable formula. Discovery, contention, configuration/Email failure, event/state read failure, Lead/message permanent failure and pre-transport state failure do not increment. Only a durably published transition to `attempting` immediately before the transport call increments. A crash in `attempting` is conservatively changed to `uncertain` with `attempt_interrupted`; automatic retry is prohibited even if transport may not actually have begun.

Allowed transitions are: absent→`eligible`; `eligible`/eligible `retry_wait`→`attempting`; `eligible` or eligible `retry_wait`→`dead_lettered` directly only for permanent pre-transport `lead_missing`, `lead_invalid`, `message_invalid`, or `archive_conflict`; `attempting`→`retry_wait`, `uncertain`, `delivered`, or `dead_lettered`; `uncertain`→`eligible` only through `authorizeDuplicateRiskRetry()` under the confirmed operator action; `uncertain`→`delivered` or `dead_lettered` only through the other confirmed reconciliation actions; matching sent archive plus nonterminal state→`delivered`. `delivered` and `dead_lettered` never leave terminal state. A direct permanent transition preserves the current attempt count and first/last attempt timestamps, clears next eligibility, records the exact permanent code, sets terminal time, and increments revision once. It never passes through `attempting`. All other transitions are `state_transition_invalid`.

### Atomic state, retry discovery and classification

State read requires exact grammar, containment, non-symlink regular mode 0600, 1–1,024 bytes, pre-open `lstat`, post-open `lstat`/`fstat` dev/inode/mode/size identity, canonical schema and final LF. Update locks the state, rereads, requires the caller's exact revision, serializes the next revision, creates `<event-id>.json.<16-lower-hex>.tmp` exclusively at 0600, writes fully, file-fsyncs, renames over the mutable state file, directory-fsyncs and removes only its validated temporary on failure. Maximum internal collision attempts are 1; stale revision returns `state_revision_stale`. Rename is allowed only for state, never event bytes. Malformed/oversized/symlink/replaced state returns `state_invalid`; no repair or transport occurs.

Retry-aware discovery retains the Phase 5B bounds and order, joins each canonical pending event to at most one state by event ID, scans at most 10,000 pending/state names, and selects at most limit 1–50 combined transport/recovery work items. No state means first-attempt eligible. `eligible` and due `retry_wait` enter the transport-eligible list; future `retry_wait`, `attempting`, `uncertain`, and `delivered` are excluded. A pending event with `dead_lettered` state enters a distinct recovery list and is never transport eligible. `attempting` is first converted to uncertain under both locks without transport. Orphan state is counted within the same 10,000-name scan; a state orphan with matching sent bytes recovers delivered, while all other orphan/conflict cases fail closed. `--retries-only` excludes no-state transport items but never excludes terminal recovery. The combined selection order remains event `created_at`, then event ID, and each selected ID appears in exactly one list. Discovery returns exact shape `array{eligible:list<string>,recovery:list<string>,deferred:int,codes:array<string,int>}` with codes sorted lexically; `deferred` counts valid future `retry_wait` records and `codes` accounts for every rejected/recovered scanned name so malformed records do not abort later safe candidates.

### Dead-letter and reconciliation

Dead-letter root is `<user-data>/goosialize-leads/v1/notification-outbox/dead-letter/<2hex>/<event-id>.json`, modes 0700/0600. The one exact order under the continuous delivery lease is: (1) CAS-publish the `dead_lettered` state with its exact reason and fsync it; (2) hard-link the still-open verified pending inode to an absent destination, verify inode identity, file-fsync and dead-letter-directory-fsync; (3) unlink pending and fsync its directory; (4) invalidate the lease and release the delivery lock. Dead-letter bytes are never rewritten or overwritten.

Before the state CAS, a crash leaves the prior state/pending and ordinary eligibility rules. After terminal CAS but before the link, pending plus terminal state prohibits transport and the next bounded discovery deterministically reacquires the delivery lease and resumes publication. After link but before its fsync, recovery verifies matching inode/bytes and completes durability; after destination durability but before pending unlink/fsync, recovery accepts only matching canonical bytes with the already-terminal matching state, then removes pending. A matching destination with matching terminal state is idempotent and does not increment revision; a matching destination with nonterminal/mismatched state or a malformed, wrong-mode, symlinked, differently sized, or byte-different destination returns `dead_letter_conflict`, preserves pending, and requires operator repair outside Phase 5C.1. Publication/I/O failure returns `dead_letter_failed` with terminal state/pending retained for later deterministic recovery. No mismatch becomes transport eligible and no event can be lost because pending is unlinked only after terminal state and destination durability.

`reconcile-notification` is operator-only: `php bin/plugin goosialize-leads reconcile-notification <64-lower-hex-event-id> <revision> (--confirm-delivered|--retry-duplicate-risk|--dead-letter) --yes`. Exactly one action and literal `--yes` are required; there are no aliases. The service calls `withLockedEvent()` and, within its one lease, securely requires the pending event, current state exactly `uncertain`, and exact revision. Confirm-delivered archives without transport then transitions `delivered`, accepting the lease's existing matching-archive recovery. Explicit duplicate-risk retry additionally requires `archiveStatus() === archive_absent` and `deadLetterStatus() === dead_letter_absent`, calls `authorizeDuplicateRiskRetry($clock->now())`, CAS-saves it, and returns without transport or movement. Dead-letter requires no sent archive, CAS-transitions terminal first, publishes unchanged bytes through the lease, then removes pending.

Duplicate-risk retry means the operator acknowledges that the prior outcome may already have delivered and authorizes one later normal bounded-batch attempt. It never invokes transport immediately and is permitted only when the uncertain state's attempt count is 1–4; attempt 5 is exhausted. Its CAS result is `eligible`, revision +1, unchanged attempt count/first/last attempt/creation time, null next eligibility/terminal time, exact result `duplicate_risk_retry_authorized`, and reconciliation-clock `updated_at`. Before lock, before validation, after validation, after state read, and after transition creation but before successful CAS, durable state remains `uncertain`; the command must be repeated and batch transport remains prohibited. During CAS, only the complete canonical old or new record is accepted. After CAS success, acknowledgment is durable and a separate later batch may process; its normal `beginAttempt()` increments the attempt and clears the audit result before transport. A crash before lock release needs no command replay. No temporary is accepted and reconciliation itself never transports.

Output is exactly `RECONCILE action=<confirm-delivered|retry-duplicate-risk|dead-letter> status=<completed|contended|rejected|failed> revision=<n-or-0>`, stderr empty. Success is `completed` with the new revision and exit 0. Missing `--yes`, invalid/missing event ID or revision, multiple/no actions, or invalid configuration is `rejected` revision 0 exit 2. Lock contention is `contended` revision 0 exit 3. Stale revision, non-uncertain state, exhausted attempt 5, missing pending event, existing sent archive, existing dead-letter, or CAS conflict is `rejected` revision 0 exit 3. I/O/atomic failure is `failed` revision 0 exit 3. No identifier, address, content, path, state value, or exception is output. `duplicate_risk_retry_authorized` is stored only in state: it is not emitted as an `ERROR` line or batch counter, and `DeliveryRetryPolicy::classify()` rejects it as a transport outcome.

Existing invocation remains `php bin/plugin goosialize-leads deliver-notifications --limit=10`; optional `--retries-only` is a value-none flag and is invalid when retry is disabled. With retry enabled, default processing includes first attempts, eligible retries, and terminal dead-letter recovery; retries-only excludes first attempts but not recovery. Lexically sorted positive `ERROR code=<code> count=<n>` lines remain first; the exact summary becomes `RESULT discovered=<n> delivered=<n> dead_lettered=<n> deferred=<n> contended=<n> failed=<n> uncertain=<n>`. Exit 0 requires contended/failed/uncertain all zero; exit 2 remains global input/configuration failure; otherwise exit 3. Required durable pre-attempt state failure prevents send; result codes add `dead_letter_conflict`, `dead_letter_failed`, `delivery_lease_invalid`, `retry_configuration_invalid`, `state_clock_invalid`, `state_invalid`, `state_orphaned`, `state_revision_stale`, `state_transition_invalid`, `state_unavailable`, `transport_exception`, `transport_uncertain`.

### Exact configuration and worker continuation

The only Phase 5C.1 configuration keys are `plugins.goosialize-leads.notifications.delivery_retry.enabled` (boolean, default `false`), `.maximum_attempts` (integer, default and sole allowed value `5`), `.delays_seconds` (integer list, default and sole allowed value `[300, 1800, 7200, 28800]`), `.processing_limit` (integer, default `10`, range 1–50), and `.state_max_bytes` (integer, default and sole allowed value `1024`). Missing keys take those defaults. Values are parsed without string/float coercion. An unknown key, wrong type, out-of-range value or nonexact fixed value disables Phase 5C.1 retry/state/reconciliation, makes `--retries-only` and reconciliation exit 2 with redacted `retry_configuration_invalid`, and leaves plugin loading, capture, outbox creation, Admin2 index, CSV export and the unchanged Phase 5B first-attempt path available. There is no dead-letter, scheduler, SMTP, recipient, sender or provider configuration key.

With retry disabled, the worker takes its exact Phase 5B path and never creates state. With retry enabled it processes deterministic eligible IDs independently. For each ID it enters `withLockedEvent()`, rereads state/revision, securely reads the pending event, checks archive status, reads the Lead and constructs the message before consuming an attempt. `archive_conflict`, Lead failure, or message failure directly invokes the state-first dead-letter transaction. Only after every permanent prerequisite passes does the worker CAS-publish `attempting` and immediately invoke the classified transport; failed CAS prohibits send. It then schedules retry, quarantines uncertainty, archives success, or dead-letters maximum-attempt failure while the same lease remains held. It continues after contention, permanent/dead-letter success, retry scheduling, uncertainty, malformed state, stale revision or filesystem failure; each non-success contributes to the exact closed counter and makes final exit 3. A failure after transport becomes uncertain. `deferred` counts future retry-wait IDs observed within the bounded scan; `dead_lettered` counts terminal movements completed or safely recovered. Dead-letter failure leaves terminal state/pending recoverable and never resumes transport.
